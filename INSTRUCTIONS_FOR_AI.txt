=== ИНСТРУКЦИЯ ДЛЯ ИИ-ПОМОЩНИКОВ (ПРОЕКТ LectureNotes) ===

1. СУТЬ ПРОЕКТА
Android-приложение для записи лекций с оффлайн-распознаванием речи в реальном времени.
Стек: Kotlin, Android SDK, Room, Coroutines/Flow, C++ (Whisper.cpp via JNI).
Архитектура: Модульный монолит (Modular Monolith).

2. ГЛАВНЫЙ ПРИНЦИП — МОДУЛЬНОСТЬ
Каждый блок изолирован и имеет чёткий контракт (интерфейс).
- Функции должны легко ВКЛЮЧАТЬСЯ и ВЫКЛЮЧАТЬСЯ без переписывания всего приложения.
- Если в блоке ошибка — переписывается ТОЛЬКО этот блок, остальные не трогаются.
- Замена одного компонента (например, движка STT) не должна ломать UI, БД или сервис.
- Аналогия: USB-порт. UI не важно, какой движок внутри — важен только контракт.

3. ПРАВИЛА РАБОТЫ (СТРОГО)
- ЧИТАТЬ ПЕРЕД ДЕЙСТВИЕМ: Перед написанием кода ИИ ОБЯЗАН прочитать текущий код файла через терминал или по ссылкам на GitHub. Гадание по памяти запрещено.
- ПОЛНАЯ ЗАМЕНА: ИИ выдает ТОЛЬКО полный код файла для замены. Точечные правки ("замени строку 15 на...") запрещены. Пользователь копирует код и полностью перезаписывает файл.
- ПО ОДНОМУ ФАЙЛУ: За один запрос ИИ работает только с ОДНИМ файлом.
- ТЕРМИНАЛ: ИИ дает команды PowerShell для открытия/создания файлов (например: `notepad app/src/main/java/...`) тоесть через команду пользователь открывает тхт файл и полност заменяй файлл на новый который ты дал.
- МОДУЛЬНОСТЬ: ИИ не имеет права нарушать границы блоков. Перед изменением блока ИИ обязан прочитать его README.txt.

4. ОБЯЗАННОСТЬ ДОКУМЕНТИРОВАНИЯ
При ЛЮБОМ редактировании кода ИИ ОБЯЗАН:
- Обновить соответствующий README.txt в папке блока
- Добавить в README раздел "ИСТОРИЯ ИЗМЕНЕНИЙ" с датой и описанием: что изменено, почему, какие контракты затронуты
- Если добавлен новый файл — создать для него описание в README блока
- Если изменён контракт (интерфейс) — явно указать, какие блоки это затрагивает

5. СТРУКТУРА БЛОКОВ
- app/src/main/cpp/ — Native (C++ JNI, Whisper.cpp). См. cpp/README.txt
- app/src/main/java/.../transcription/ — Transcription (Обертка над JNI). См. transcription/README.txt
- app/src/main/java/.../data/ — Data (Room DB, DAO, Entity). См. data/README.txt
- app/src/main/java/.../ui/ — UI (ViewModel, Screens). См. ui/README.txt
- app/src/main/java/.../RecordingService.kt — AudioCapture (Foreground Service, Flow).
- app/src/main/java/.../MainActivity.kt — Presentation (Связывает блоки).

6. ТЕКУЩИЙ СТАТУС
Основа приложения готова:
- Модель Whisper грузится один раз в памяти.
- RecordingService пишет аудио и отдает чанки через SharedFlow.
- MainActivity подписана на Flow, транскрибирует через WhisperTranscriber и сохраняет результат в Room DB.
- Удалены старые дубликаты и синглтоны (AudioBuffer).
- Созданы README.txt для каждого блока с описанием контрактов.

7. ЧТО ДЕЛАТЬ ДАЛЬШЕ (ЗАДАЧИ)
- Создать экран списка записей (RecyclerView / Jetpack Compose) с использованием RecordingViewModel.allRecordings.
- Создать экран просмотра/редактирования конкретной записи.
- Добавить функцию экспорта текста (txt/md).
- Оптимизировать транскрибацию (добавить контекст между чанками, чтобы слова не рубились).
- Добавить слой UseCase (RecordLectureUseCase) для координации блоков.

8. ЗАПРЕТЫ
- Не использовать глобальные синглтоны (object) для передачи данных между Service и UI. Только Flow/StateFlow.
- Не дублировать код в разных блоках.
- Не писать бизнес-логику в Activity/Fragment. Только в ViewModel или UseCase.
- Не переписывать работающие блоки "на всякий случай". Рефакторинг только по конкретной боли.
- Не нарушать контракты блоков без явного согласования и обновления всех зависимых README.
